## Goal

Ship 2.12.2 with a DMG build that never drives Finder, fix the confirmed bugs left from Plan 025's
P2 pass, and use the published 2.12.2 to test the in-app updater from the installed 2.12.0.

## Phase 1: DMG build without Finder

`scripts/build-dmg.sh` lays out the disk-image window with Finder AppleScript. It opens the
mounted image and sets the container window's bounds, view, toolbar, and status bar. With tab mode
set to Always, that changed the user's existing Finder window during the v2.12.1 build.

1. Replace the AppleScript layout with [`dmgbuild`](https://pypi.org/project/dmgbuild/) 1.6.7,
   which the user chose. It writes the window geometry, background, and icon positions directly
   into the image's `.DS_Store`.
   - Install it into a throwaway venv at `build/dmg-venv`, which is ignored by git and created on
     demand.
   - Keep the settings in `scripts/dmg-settings.py`.
2. Keep the look: a 480×540 window, the generated arrow background, 100 px icons, `zMD.app` at
   (240, 140), `Applications` at (240, 400), no toolbar or status bar, and zlib-9 UDZO
   compression.
3. Remove the notarization branch (out of scope, and it repackaged through Finder) and
   `scripts/.notary-config.example`. The script always builds ad-hoc; `NOTARIZE=0` is accepted
   and ignored.
4. Keep the EXIT trap that unregisters development copies.

**Verify**

- The build runs with no Finder windows opened or changed. Check the window list before and after.
- The DMG mounts `-nobrowse` and contains `zMD.app`, `Applications`, `.background/`, and a
  `.DS_Store`.
- Read the `.DS_Store` back with the `ds_store` package and confirm the window bounds, background
  alias, and icon positions.

### 2026-09-29 Phase 2: fixes (done, `341629a`)

- **F1 View menu.** `CommandMenu("View")` became `CommandGroup(before: .toolbar)`. The menu bar
  now reads `Apple | zMD | File | Edit | View | Format | Tab | Window | Help`, and View holds
  zMD's items followed by Enter Full Screen.
- **F4 and F5 line numbers and the stray line.** There were two root causes:
  - `SourceEditorView` never set the ruler's `clientView`, so `LineNumberGutter` returned before
    drawing anything, including its grey background.
  - Its visible-glyph query passed text-view coordinates where text-container coordinates were
    expected, which are offset by the 30 pt inset. At the top of a document that skipped line 1.
    This was found with temporary logging that has since been removed.

  The fix adds `installGutter(in:for:)`, which sets the client view, converts the rect by
  `textContainerOrigin`, and sets `clipsToBounds = true` on macOS 14 and later. That stops the
  ruler's edge line from crossing the tab bar and toolbar. Screenshots show lines 1–723 numbered
  in Source and Split mode with soft-wrap continuations unnumbered
  (`screens/2122-gutter-*`). `LineNumberGutterTests` covers the client view and clipping.
- **F3 outline animation.** The `@AppStorage` toggle lost its `withAnimation` transaction, so
  there is now a scoped `.animation(Motion.standard, value: showOutline)`. With Reduce Motion
  off, the outline animates over 200 ms in 5 frames instead of 1
  (`video/2122-outline-open-rm-off.*`).
- **F2 Reduce Motion.** A new `fadeInUnderReduceMotion()` modifier fades inserted chrome in its
  own transaction while layout stays instant. It is applied to the outline, the folder sidebar,
  and the find bar. With Reduce Motion ON, the outline fades in place with no slide, and the
  find bar appears in place and fades (`video/2122-*-rm-on.*`). Reduce Motion was switched ON in
  System Settings → Accessibility → Motion for the test and restored OFF afterwards; the other
  Motion switches are unchanged.
- **F6 code-block frame: documented, not changed.** The frame is drawn with box-drawing
  characters: a fixed 78-column top and bottom line at 11 pt, a left `│` per line, and no right
  border. The line background runs the full width. Adapting it to the pane width means
  rebuilding code blocks as `NSTextBlock`s, which affects copy, print, and export. That is a
  separate design change, not a contained fix.
- **Warnings.** A full recompile under Xcode 27 surfaced three pre-existing
  `#ImplicitStrongCapture` warnings (in `SourceEditorView`, `MarkdownTextView`, and
  `DocumentManager`), fixed with weak captures in the outer closures. A full 74-file compile then
  had 0 warnings.
- **Tests.** 119 passed and 0 failed, with 0 warnings.

**Updater test**, from the installed `/Applications/zMD.app` 2.12.0 via zMD → Check for Updates…

- The sheet offered 2.12.2 with its release notes, and "Update Now" downloaded the image.
- The install was then refused: "Update failed — Cannot determine current bundle Team ID;
  refusing to auto-install" (`screens/2122-updater-*`).
- `/Applications/zMD.app` stayed 2.12.0 and intact, with no staging copy or mounted volume left.

**Cause.** `UpdateManager` uses the running app's Team ID as its trust anchor
(`currentTeamID()`, `verifySignature`). Ad-hoc signed builds have no Team ID, so automatic
install can never succeed for this fork's releases. The check still works, and the user must
update by hand from the DMG. Any change to the updater's trust model is a security decision for
the user:

- offer a download or open-the-release action instead of "Update Now" when there is no Team ID;
- or verify the DMG's SHA-256 against the release asset's published `digest`, plus the bundle
  identifier and signature validity, as an ad-hoc trust anchor.
